## 1. Caveat — most pre-2026 numbers in this repo are unreliable

The pre-2026 bench reports made claims like:

- "**QUIC throughput >1 GB/s**"
- "**stream latency <1 ms**"
- "**multiplexing <100 µs**"
- "**schedule overhead <100 ns**"
- "**DTW <10 ms for n=1000**"

[ADR-0009](adr/0009-honest-benchmarks.md) audited every one of these
and found:

- The QUIC benches run against an **in-memory `MockConnection`** with
  a `tokio::time::sleep` (`benches/quic_bench.rs:71-85`). No real
  `quinn`, no UDP socket, no TLS handshake, no congestion control.
  The numbers measure tokio's timer + atomic increments, **not QUIC**.
- The scheduler "<100 ns" claim is **mathematically incompatible**
  with the implementation, which acquires three `parking_lot::RwLock`
  write guards per `schedule()` call (~20–40 ns each uncontended).
  The bench also builds a fresh `RealtimeScheduler` inside `b.iter`
  — construction overhead dominates the measurement.
- The end-to-end benches (`benches/lean_agentic_bench.rs:233-303`)
  construct a full `LeanAgenticSystem` with 4 `Arc<RwLock<_>>` plus
  4 subsystems **inside** `b.iter`. Easily 90% of the measurement
  is `Arc::new` + `RwLock::new` overhead, not the pipeline.
- The DTW/LCS/edit-distance micro-benches (small-n) are defensible
  as upper bounds.

**Of 22 advertised targets in the old `BENCHMARKS_SUMMARY.md`, ~4
are credible.** The rest are either marketing numbers or
construction-overhead-polluted. Treat any claim not regenerated by
the rewrite below with caution.

benches under `crates/*/benches/`:

## 3. Running benches

```bash
# Compile-check all benches without running.
cargo bench --workspace --no-run

# Full bench run. Takes ~5–15 minutes on a modern host.
cargo bench --workspace

# One specific crate.
cargo bench -p midstreamer-temporal-compare

# One specific bench inside criterion (regex match).
cargo bench -p midstreamer-scheduler -- schedule_overhead

# Capture machine-readable output.
cargo bench --workspace -- --output-format=bencher
```

Per-bench HTML reports land under
`target/criterion/<bench>/report/index.html` by default; criterion's
config knobs (sample size, warmup, measurement time) live next to
each bench in `criterion_group!{ ... }`.

## 4. CI integration

`.github/workflows/rust-ci.yml` runs benches on every `push` to
`main` (line ~152, `benchmark` job). The job:

1. Installs the workspace rustup toolchain.
2. Restores the rust-cache.
3. Runs `cargo bench --workspace --all-features -- --output-format
   bencher | tee benchmark-results.txt`.
4. Uploads results via `benchmark-action/github-action-benchmark@v1`
   with `alert-threshold: 150%` — any 1.5× regression triggers a PR
   comment.

The alert-threshold is **not** an SLO. Tracking regression
percentages over the baseline is a useful signal but says nothing
about whether the absolute number is fast enough. Per
[ADR-0033](adr/0033-scheduler-slo-contract.md), the scheduler is
the first crate getting a real SLO contract (p50/p99/p999 per
workload, per contention level) with CI-enforced thresholds. The
SLO bench lives at `benches/scheduler_slo_bench.rs` once that ADR
ships.

## 5. The ADR-0009 rewrite plan

When the bench-rewrite PR (currently a follow-up to
[ADR-0009](adr/0009-honest-benchmarks.md)) lands, each of these
changes ships:

1. **Mock QUIC bench → real loopback `quinn` endpoint.**
   `benches/quic_bench.rs` will spin up a `quinn::Endpoint` server
   on a unix-domain (or 127.0.0.1) loopback, drive real packets
   through real congestion control, and assert latency + throughput
   against thresholds checked into source.
2. **Construction overhead removed.** Every `b.iter(|| { let s =
   Struct::new(); s.method(...) })` becomes
   `b.iter_batched(|| Struct::new(), |s| s.method(...),
   BatchSize::SmallInput)`.
3. **`criterion-perf-events`** adds IPC + L1/L2/LLC miss counters
   on Linux runners so we can see *why* a regression happened.
4. **`dhat` allocation-regression tracking** for the hot path
   (per [ADR-0006](adr/0006-zero-copy-bytes-streaming.md)). Caps
   bytes-allocated-per-chunk at the value committed in the bench.
5. **`hdrhistogram` for tail percentiles** on the scheduler SLO
   bench (per [ADR-0033](adr/0033-scheduler-slo-contract.md)). p50
   / p99 / p999 / max across 1 / 4 / 16 / 64 producer threads.

The CI bench job is *not* a gate today; ADR-0009 promotes it to
gating with a configurable per-metric tolerance (default 5% warn,
10% fail).

## 8. Reporting a bench regression

If `cargo bench --workspace` shows a >5% regression on a metric
you care about:

1. **Check the build flags.** `cargo bench` ignores `[profile.dev]`
   knobs and uses `[profile.bench]` (defaults to `opt-level = 3`,
   `debug = false`). Confirm your build matches by inspecting the
   first lines of the criterion output.
2. **Check the host load.** Background processes (browser, IDE,
   sync clients) dominate p99 noise. Run benches on an otherwise
   idle host or in a sandbox.
3. **Cite the criterion JSON.** Open an issue using the
   `bug_report` template; attach
   `target/criterion/<bench>/new/estimates.json` and the
   `report/index.html` so reviewers can see the distribution, not
   just the mean.
4. **Don't quote a hand-typed number.** Per Section 1, that's how
   we got into the prior trouble.
