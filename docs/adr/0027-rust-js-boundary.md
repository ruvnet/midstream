# 0027 — Rust ↔ JS boundary: WASM in-process, MCP cross-process; retire the HTTP shim

- **Status:** Proposed
- **Date:** 2026-05-13
- **Deciders:** @ruv
- **Tags:** boundary, ipc, wasm, mcp

## Context and Problem Statement

There are currently **four parallel ways** for a JavaScript caller to
reach the Rust core, none of which is canonical:

| Path | Location | Transport | Use case (apparent) |
|------|----------|-----------|----------------------|
| WASM bindings (3 crates) | `wasm/`, `wasm-bindings/`, `npm-wasm/` | in-process WASM | Browser + Node in-process |
| HTTP RPC | `lean-agentic-js/src/client.ts` (axios) | HTTP/REST | Talks to a Rust HTTP server (which isn't in this repo) |
| WebSocket/SSE | `npm/src/openai-realtime.ts`, `npm/src/streaming.ts` | WS / SSE | Streaming text + audio from OpenAI Realtime directly (not the Rust core) |
| MCP server | `npm/src/mcp-server.ts` (410 LOC) | MCP protocol (stdio/HTTP) | Other agents reaching midstream |

The HTTP RPC path (`lean-agentic-js`) is the most problematic: it
imports from `axios` and assumes a Rust HTTP server exists at some
URL, but **there is no Rust HTTP server in this repo**. The
TypeScript code defines URL endpoints (`/agent`, `/knowledge`,
`/stream`) that nothing serves; the package is shippable as a stub
but the integration is unimplemented end-to-end.

Meanwhile, `npm/src/quic-integration.ts` (436 LOC) reimplements a
QUIC client in TS that talks to *some* QUIC server (presumably the
Rust `quic_server` example) but the contract — what messages,
which framing, what schema — lives nowhere except both sides' source.

The result is a confused boundary: the same concept (e.g. "send a
chunk for sanitization") can be expressed in 2–3 different ways, each
with its own framing.

## Decision Drivers

- **One canonical in-process path.** When JS code wants to call into
  Rust without a network hop, there should be exactly one answer.
- **One canonical cross-process path.** When JS code wants to call a
  *running* Rust service, there should also be exactly one answer.
- **Schema-first.** Whichever paths survive must derive their
  message shapes from a single source of truth (TypeScript types
  generated from Rust types or vice versa).
- **Retire the HTTP path** because it duplicates concerns and has
  no server-side implementation.

## Considered Options

1. **Status quo.** Four paths. Confusion grows.
2. **Pick WASM as in-process canonical; MCP as cross-process
   canonical; retire the HTTP and the bespoke QUIC paths in JS.**
3. **Pick HTTP/REST as cross-process canonical; build the
   server-side.** Larger scope; less aligned with the existing MCP
   investment.
4. **Pick gRPC + tonic (already a transitive dep via arrow-flight)
   as cross-process canonical.** Type-safe; mismatched with MCP's
   stdio model.

## Decision Outcome

**Chosen option: Option 2.**

The two canonical paths are:

### In-process: WASM

JS calls into Rust via the canonical WASM binding (`@midstream/wasm`,
post-[ADR-0003](0003-wasm-consolidation.md)). The binding's
`#[wasm_bindgen]` signatures are the schema; types flow through
`tsify`-generated `.d.ts`.

Use cases: browser dashboards, Node CLIs that don't need a separate
service, edge runtimes (Cloudflare Workers, Deno Deploy).

### Cross-process: MCP

JS (or any other client) calls a running Rust service via the
**Model Context Protocol** (MCP), which the codebase already invests
in (`npm/src/mcp-server.ts` exists today on the JS side; a Rust MCP
server is the missing half). MCP supports stdio and HTTP transports;
both are wire-formatted JSON-RPC.

Use cases: long-running Rust services, agent-to-agent communication,
the swarm orchestration model already in `CLAUDE.md`.

### Retired

- **HTTP RPC in `lean-agentic-js`.** The axios client and `/agent`,
  `/knowledge`, `/stream` endpoints are deleted; the package is
  rebuilt on top of either the WASM path (in-process) or an MCP
  client (cross-process).
- **Bespoke QUIC framing in `npm/src/quic-integration.ts`.** The
  QUIC transport survives at the *Rust* layer (cf.
  [ADR-0021](0021-quic-implementation-quinn.md)) but the JS-side
  custom framing is replaced by the MCP-over-QUIC transport (when
  available) or by WebTransport via the WASM binding.

### Schema source

- Rust types in `crates/midstreamer-*` are the source.
- `ts-rs` (`#[derive(TS)]`) generates `.d.ts` files into
  `packages/wasm/types/` at `cargo build` time.
- MCP request/response schemas are JSON-Schema, generated by
  `schemars` from the same Rust types.

### Positive consequences

- One in-process answer (WASM), one cross-process answer (MCP).
  Reviewers can challenge any new path with "why not WASM or MCP?".
- TS types regenerate from Rust types automatically; drift becomes a
  build error, not a runtime bug.
- The (non-existent) HTTP server in `lean-agentic-js` stops being
  shipped as if it works.

### Negative consequences

- `lean-agentic-js`'s public surface changes substantially.
  Mitigated by [ADR-0026](0026-typescript-monorepo.md)'s decision to
  drop it from 1.0 → 0.2.
- A Rust-side MCP server must be implemented to honour the
  cross-process choice. That's real work (~2 weeks); we should not
  ship a half-implementation.

## Implementation notes

- Add `ts-rs = "8"` and `schemars = "0.8"` to root
  `[workspace.dependencies]`. Annotate the Rust types that cross the
  boundary with `#[derive(TS, JsonSchema, Serialize, Deserialize)]`.
- Replace `lean-agentic-js/src/client.ts`'s axios calls with an MCP
  client built on `@modelcontextprotocol/sdk` (already a dep in
  `npm/package.json:50`).
- Implement a Rust MCP server in `crates/midstreamer-mcp-server` (new
  crate, post-[ADR-0001](0001-single-cargo-workspace.md)) exposing
  the same tool surface as the existing `npm/src/mcp-server.ts`.
  Mark the TS MCP server `#[deprecated]` once the Rust side reaches
  parity.
- Delete `npm/src/quic-integration.ts` and its tests; the QUIC
  transport story stays in Rust + WASM.
